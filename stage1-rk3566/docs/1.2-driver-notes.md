## 零、⭐ 构建环境方案（重要，以后编模块都用这个）

### 结论：**在 x86 虚拟机上交叉编译，产物 scp 到板卡运行**

**为什么不能在板卡上编**（详见 **K-032**）：

```
内核构建产物分两类：
  目标代码（kernel/modules） → 运行在目标板 → 目标架构（aarch64）
  host 工具（fixdep/conf/modpost） → 运行在【构建机】 → 构建机架构（x86_64）
```

内核在 x86 上交叉编译 → host 工具是 **x86 二进制** → 拷到 aarch64 板卡**执行不了**
（`scripts/basic/fixdep: Exec format error`）

> ⚠️ 且**无法就地重建**：`make scripts` → 需要 `syncconfig` → 需要 `conf` → **它也是 x86 的**（死锁）

**澄清**：板卡**能**编译普通程序（原生 gcc + libc 齐全）；受限的只是"依赖外来内核构建树"的东西。

### 关键路径与命令（x86 虚拟机）

| 项 | 值 |
|---|---|
| **内核源码树** | **`~/tspi_sdk/kernel-6.1/`**（含 `.config` / `Module.symvers` / `vmlinux` / host 工具） |
| 其它相关 | `~/tspi_sdk/u-boot/`、`~/tspi_sdk/output/recovery-kernel/` |
| 交叉工具链 | `aarch64-linux-gnu-` 11.4.0 |

**编译命令**：

```bash
make -C ~/tspi_sdk/kernel-6.1 \
     M=$PWD \
     ARCH=arm64 \
     CROSS_COMPILE=aarch64-linux-gnu- \
     modules
```

**`ARCH` 和 `CROSS_COMPILE` 必须显式给**——在 x86 上不指定，内核构建系统会按 x86 编译。

**完整工作流**：

```bash
# ── 板卡：写代码
cd ~/edge-ai-dual-node/stage1-rk3566/drivers/edge_ai_evt

# ── 虚拟机：拉源码
scp -r lihaihui@192.168.31.151:~/edge-ai-dual-node/stage1-rk3566/drivers/edge_ai_evt ~/

# ── 虚拟机：编译
cd ~/edge_ai_evt
make -C ~/tspi_sdk/kernel-6.1 M=$PWD ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- modules
file edge_ai_evt.ko        # ★ 必须验证：ARM aarch64

# ── 虚拟机：传回板卡
scp edge_ai_evt.ko lihaihui@192.168.31.151:~/edge-ai-dual-node/stage1-rk3566/drivers/edge_ai_evt/

# ── 板卡：加载验证
sudo insmod edge_ai_evt.ko
lsmod | grep edge_ai
dmesg | tail -5
sudo rmmod edge_ai_evt
```

## 一、驱动是什么？——"一切皆文件"的另一半

1.1 学的是**用**内核提供的接口（gpio / leds）。但内核不可能为每种硬件都写驱动。

> **驱动 = 你写给内核的一段代码，把某个硬件（或逻辑功能）翻译成"文件操作"。**

用户态：
```c
int fd = open("/dev/edge_ai0", O_RDWR);
ioctl(fd, CMD_SET_X, &arg);
read(fd, buf, 16);
```
**这三行背后被调用的，就是你写的函数。**

**MCU 类比**：和你在 STM32 里注册中断服务函数是同一思路——**你提供函数，框架在对的时机调用它**。只是 Linux 的"框架"管的是**整个文件系统接口**。

## 二、`file_operations`：一张"函数指针表"

内核不关心你叫什么、做什么，只要求你**填一张表**：

```c
struct file_operations {
    ssize_t (*read)   (struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)  (struct file *, const char __user *, size_t, loff_t *);
    long    (*unlocked_ioctl)(struct file *, unsigned int, unsigned long);
    int     (*open)   (struct inode *, struct file *);
    int     (*release)(struct inode *, struct file *);   /* = close */
    ...
};
```

**调用链**：

```mermaid
graph LR
    A["你的程序<br/>read(fd, buf, n)"] -->|系统调用| B["VFS 层"]
    B -->|查该文件的 f_op 表| C["你的 .read 函数"]
    C -->|填数据| D["硬件 / 内部状态"]
```

**"注册驱动"的本质 = 把你的函数指针交给内核。**

## 三、内核模块：热插拔的代码

```
insmod edge_ai_evt.ko  →  代码装进内核 + 调用 module_init
rmmod  edge_ai_evt.ko  →  调用 module_exit + 释放内存
```

**两条代价**：
- **与内核版本强绑定**（`vermagic` 不匹配直接拒绝，K-009）
- **跑在内核空间**——出错不是"进程崩了"，而是**整个系统崩了**

## 四、⚠️ 内核空间 vs 用户空间（本节最重要）

| | 用户空间 | 内核空间 |
|---|---|---|
| **崩溃后果** | 进程死掉 | **整个系统挂掉** |
| **可用库** | libc（`printf`/`malloc`） | **只有内核 API**（`printk`/`kmalloc`） |
| **内存访问** | 只能访问自己的地址空间 | **不能直接解引用用户态指针** |
| **调试** | gdb / printf | `printk` + `dmesg`（**没有 gdb**） |

### 为什么不能直接解引用用户态指针

**① 安全性**——用户指针可能是恶意的：
```c
/* 用户态 */
char *evil = (char *)0xffff888000000000;   /* 指向内核地址 */
ioctl(fd, CMD_WRITE, evil);
/* 驱动里若直接写 *(char *)evil = 'x';
   → 等于给了用户"任意内核内存写"权限 💥 */
```

**② 有效性**——用户地址可能被换出（在 swap 里）。直接访问触发缺页，而内核在很多上下文**不能休眠** → 死锁。

**③ 语义**——内核**不应信任**用户空间的任何数据。

**所以内核给你安全的搬运工**：

```c
unsigned long copy_to_user  (void __user *to, const void *from, unsigned long n);
unsigned long copy_from_user(void *to, const void __user *from, unsigned long n);
```

| 细节 | 说明 |
|---|---|
| **返回值** | **未成功拷贝的字节数**——`0` 才算成功，**必须检查** |
| `__user` 标记 | 告诉编译器"这是用户空间指针" |
| **可能休眠** | 不能在中断上下文调用 |

> 💡 **记住**：**内核和用户空间之间，只有"拷贝"，没有"共享"。**

## 五、两条铁律 + 三个意外

**铁律**：

| # | 规则 | 原因 |
|---|---|---|
| 1 | **不能用 libc**：`printf`→`printk`、`malloc`→`kmalloc` | 内核空间没有 libc |
| 2 | **不能浮点运算** | 内核不保存 FPU 状态 |

**意外**：

| # | 现象 | 原因 |
|---|---|---|
| 3 | **栈很小**（通常 8~16KB） | 别放大的局部数组 |
| 4 | **`printk` 输出到 `dmesg`，不在终端** | 它写内核环形缓冲区 |
| 5 | 需要睡眠用 `msleep()` | 不是 `sleep()` |

```c
MODULE_LICENSE("GPL");               /* ★ 必须写 */
MODULE_AUTHOR("lihaihui");
MODULE_DESCRIPTION("Edge AI dual-node: event queue char device (stage 1.2)");
```

```makefile
obj-m += edge_ai_evt.o

KDIR := /lib/modules/$(shell uname -r)/build
```

> ⚠️ **不是你的 Makefile 在编译**——而是**内核的构建系统在编译**，你的 Makefile 只是个"转发器"。

## 七、第 2 次成果（2026-09-27 下半场）✅ `file_operations` + 自动创建设备节点

### 7.1 代码结构（`edge_ai_evt.c` 第 2 版）

```
# 1. 元信息：MODULE_LICENSE / MODULE_AUTHOR / MODULE_DESCRIPTION / MODULE_VERSION("0.2")
# 2. 回调：
#      edge_ai_open()     → printk
#      edge_ai_release()  → printk
#      static const struct file_operations edge_ai_fops = {
#          .owner = THIS_MODULE, .open = ..., .release = ..., };
# 3. 全局：int major; struct class *edge_ai_class; struct device *edge_ai_device;
# 4. init：
#      major = register_chrdev(0, DEV_NAME, &edge_ai_fops)
#           → 一步搞定：申请主设备号 + 把 fops 挂到内核（成功返回主设备号，负数=失败）
#      class_create(THIS_MODULE, DEV_NAME)   → /sys/class/edge_ai 出现
#      device_create(class, NULL, MKDEV(major,0), NULL, "edge_ai0")
#                                            → 内核发 uevent，udev 建 /dev/edge_ai0
# 5. exit：严格逆序释放（device_destroy → class_destroy → unregister_chrdev）
```

### 7.1b ⚠️ 一个容易混淆的点：`register_chrdev` 是「一步到位」的老接口

内核里注册字符设备有**两套写法**，极易搞混：

| | 老接口（第 2 次实际用的） | 新接口（现代驱动更常见） |
|---|---|---|
| 申请设备号 | `register_chrdev(0, name, fops)` **一个函数全包** | `alloc_chrdev_region(&dev, 0, 1, name)` |
| 挂 fops | ↑ 同上 | `cdev_init(&cdev, fops)` + `cdev_add(&cdev, dev, 1)` |
| 释放 | `unregister_chrdev(major, name)` | `cdev_del()` + `unregister_chrdev_region()` |
| 占用范围 | **独占该主号下全部 256 个次设备号** | 可精确指定申请几个次设备号 |
| 内幕 | 内部就是 `__register_chrdev(major, 0, 256, name, fops)` | — |

**怎么选**：
- 一个主设备号下只对应一个设备（本项目就是）→ `register_chrdev` 足够，代码最短
- 一个驱动管多个设备（4 个串口 / 多个摄像头）→ 必须用 `alloc_chrdev_region`+`cdev`，否则次设备号不够分

**MCU 类比**：`register_chrdev` ≈ 调用 HAL 的初始化函数一键配好；`alloc_chrdev_region`+`cdev` ≈ 自己写 RCC 时钟 + NVIC 优先级 —— 麻烦但可控。

> 📝 **本项目实际用的是 `register_chrdev`**（第 2 次实测）。笔记初稿曾误写成 `alloc_chrdev_region`+`cdev`，已于 2026-09-28 修正。

### 7.2 ⭐ 为什么需要"两条线"

这是第 2 次最重要的认知：

| 线 | 干什么 | 不做会怎样 |
|---|---|---|
| **注册线**（`register_chrdev`） | 把**设备号 ↔ fops** 告诉内核 | `open("/dev/edge_ai0")` 内核找不到处理函数 |
| **class/device 线**（`class_create` + `device_create`） | 触发 **udev 在 `/dev` 建节点** + 在 `/sys/class` 建目录 | `/proc/devices` 里有你的驱动，但 **`/dev` 下空无一物**，用户态根本打不开 |

**实验证明（见 7.4 实验②）**：只留第一条线时，`/proc/devices` 有 `edge_ai_evt`，但 `ls /dev/edge_ai*` 报 `No such file`。

**MCU 类比**：
- 注册线 ≈ 把中断向量表填好（"有事找哪个函数"）
- class/device 线 ≈ 把外设引脚接到排针上（"外面的人怎么接进来"）
- 两者都做，别人才能真正用上你这个外设。

### 7.3 ⭐ 三个函数的返回值语义（`IS_ERR` vs `< 0`）

| 函数 | 成功返回 | 失败返回 | 怎么判错 |
|---|---|---|---|
| `register_chrdev` | ⚠️ **主设备号本身（正数）** | 负的 errno | `if (major < 0)` |
| `class_create` / `device_create` | **指针** | `ERR_PTR(-errno)` | `if (IS_ERR(p))`，取值用 `PTR_ERR(p)` |

> ⚠️ **`register_chrdev` 是个特例**：成功时返回的是**主设备号本身**（正数），**不是 0**。
> 所以必须写 `if (major < 0)` —— 不能写 `if (!major)`，因为**主设备号 0 本身是合法的**（只是动态分配通常不会给 0）。
> **教训**：内核函数「成功返回什么」因函数而异，**必须查头文件注释/文档**，不能凭直觉。

**共同点：内核错误码都是"负的"**（`-EINVAL`、`-ENOMEM`…），**不要**自己编正数返回。
**MCU 类比**：HAL 库返回 `HAL_StatusTypeDef` 枚举；内核的"错误返回"是**约定俗成**的——函数直接返回负数，**没有统一枚举类型**，所以必须知道每个函数的约定。

### 7.4 四个实验（实测记录）

#### 实验①：设备节点自动出现（对比 `mknod`）

```bash
sudo insmod edge_ai_evt.ko
ls -l /dev/edge_ai0            # → crw------- 1 root root 510, 0
cat /proc/devices | grep edge  # → 510 edge_ai_evt
```
- **主设备号 510**：动态分配，内核**从高位往下找**空号
- **权限 `root:root`**：这是 **udev 的默认规则**给的（**呼应 1.1** 学的 `/etc/udev/rules.d/`）
- 对比第 1 次：那时要手动 `mknod /dev/edge_ai0 c 510 0`，还要自己算主次号

#### 实验②：设备号 ≠ 设备节点（把 class/device 注释掉再编译）

| | 有 class/device | 注释掉后 |
|---|---|---|
| `/proc/devices` | 有 `510 edge_ai_evt` | **仍有** `510 edge_ai_evt` |
| `/dev/edge_ai0` | ✅ 存在 | ❌ **不存在** |
| `/sys/class/edge_ai/` | ✅ 存在 | ❌ 不存在 |

**结论**：cdev 只让内核"认识"这个设备号；**只有 `device_create` 才会通知 udev 去建 `/dev` 节点**。

#### 实验③：`/sys/class` 里的落地

```bash
cat /sys/class/edge_ai/edge_ai0/dev   # → 510:0   ← 内核眼中这个设备的身份
ls /sys/class/edge_ai/edge_ai0/       # → dev  power  subsystem  uevent
ls -l /sys/class/edge_ai/edge_ai0     # → ../../devices/virtual/edge_ai/edge_ai0
```
**`virtual`** 的来源：`device_create` 的 parent 传了 `NULL` → 内核把设备挂到**虚拟总线**下。
（真实硬件设备（如 I2C 上的传感器）会挂在 `.../i2c-3/3-0050/` 这样的物理路径下。）

#### 实验④：引用计数保护（内核的"安全气囊"）

```bash
# 终端 A：只 open，不 read（read 会立刻返回 EINVAL 退出，挂不住）
python3 -c "f=open('/dev/edge_ai0','rb'); input('按回车退出')"
# 终端 B：
sudo rmmod edge_ai_evt     # → rmmod: ERROR: Module edge_ai_evt is in use
```
**原理**：每次 `open` 内核给模块计数 **+1**，`release` 时 **-1**。计数非 0 时 `rmmod` 被拒绝。
**为什么必须有**：模块被卸载后**代码段会被释放**；如果还有用户态进程持有 `open` 的文件描述符，下一次 `read` 就会**跳到已释放的内存** → 内核崩溃（oops）。
**MCU 类比**：相当于"正在用 DMA 的外设不许改寄存器"——硬件层面靠你自己保证，内核层面**框架帮你兜住**。

### 7.6 新知识：`EACCES` 与 `EINVAL` 来自不同的层（→ K-034）

| 错误 | 现象 | 来自哪层 | 说明 |
|---|---|---|---|
| `Permission denied`（`EACCES`） | 普通用户 `open()` | **VFS 权限检查** | 节点权限不够，**驱动代码根本没执行** |
| `Invalid argument`（`EINVAL`） | root `read()` | **VFS 调 fops** | 权限过了，但 `.read` 是 `NULL` → 返回 `-EINVAL` |

**排错指引**：
- 见到 `Permission denied` → 查**设备节点权限** / udev 规则（`ls -l /dev/xxx`）
- 见到 `Invalid argument` → 查**驱动实现了哪些 fops 回调**（没实现的那个就是 `-EINVAL` 的来源）

**为什么 `cat /dev/edge_ai0` 报 `Invalid argument`**：
`cat` = `open` + 循环 `read` + `close`。当前 fops 只有 `.open`/`.release`，**`.read == NULL`** → VFS 立刻返回 `-EINVAL`，`cat` 打印错误退出。
（**这也解释了实验④为什么必须用 Python**：`cat` 会立刻退出，根本挂不住。）

### 7.7 需要用户态能访问 `/dev/edge_ai0`（可选）

当前 `crw------- root root` → 普通用户打不开。两种方案：
1. **加 udev 规则**（和 1.1 的 gpiochip 玩法一致）
2. **`chmod`/`chown` 手动改**（重启后失效，仅调试用）

| 1 | **`printk` 宏与字符串之间加空格** | `printk(KERN_INFO "…")` | 现在写成 `KERN_INFO"…"`，能编译但可读性差 |
| 2 | **日志加模块名前缀** | `"edge_ai_evt: device opened\n"` | 系统里模块多，`dmesg` 里分不清是谁打的 |
| 3 | ⭐ **改用 `pr_fmt` + `pr_info`/`pr_err`** | `#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt` | **现代内核标准写法**：前缀自动加、不用手写 `KERN_xx`、不会被忘掉 |
| 4 | **`MODULE_VERSION` 升到 `"0.3"`** | 功能变化同步版本 | 方便 `modinfo` 确认板卡上跑的是哪个版本 |

**⚠️ `pr_fmt` 的坑**：**必须写在所有 `#include` 之前**！
因为它是个宏，`pr_info` 在 `include/linux/printk.h` 里定义时会"记住"当时的 `pr_fmt` —— 写在 `#include` 之后就失效了。
（**MCU 类比**：类似在 `#include "xxx.h"` 之前必须先 `#define` 配置宏（如 `#define HAL_UART_MODULE_ENABLED`），顺序错了配置就不生效。）

**改进后的代码开头长这样**：
```c
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt   // ← 必须是文件的第一行（注释除外）

#include <linux/module.h>
#include <linux/fs.h>
...
pr_info("device opened\n");        // dmesg 里显示 "edge_ai_evt: device opened"
pr_err("register_chrdev failed: %d\n", major);
```

### 9.2 ⭐ 用户自己发现的改进：用 `*ppos`，不用全局 `kpos`

计划里给的是「全局 `kpos` 记录读到哪了」。**用户改用了 `*ppos`（即 `struct file::f_pos`），这个改动更正确**：

| 方案 | 进程 A `cat` 读完后，进程 B 再 open | 结果 |
|---|---|---|
| 全局 `kpos` | `kpos` 已 == `klen` | B **读到空** ❌ |
| **`*ppos`** | B 的 `f_pos` 从 **0** 开始 | B **能重新读到全文** ✅ |

**原因**：`struct file` 是**每次 `open` 创建一个**，所以 `f_pos` 是**每 fd 独立**的。
内核里所有正规驱动（`/proc`、sysfs）都这么做——**读位置绝不放在全局变量里**。

**实测证据**：
```bash
sudo cat /dev/edge_ai0        # → Hello from edge_ai_evt module!
sudo cat /dev/edge_ai0        # → 又读到全文（若是全局 kpos 这里会是空）
sudo head -c 5 /dev/edge_ai0  # → Hello
```

> 📝 **两点语义区分**（第 4 次讨论时用到）：
> - **可重复读**（像 `/proc/xxx`）：每次 `open` 从头读 → 适合展示“当前状态”
> - **一次性消费**（像管道/队列）：读走就没了 → 适合事件流
> 本项目当前实现是前者（用 `*ppos`），是教学阶段的有意简化。

### 9.3 三个“动手前必想”的问题（含答案）

**Q1：缓冲区空了，返回 `0` 还是 `-EAGAIN`？**

| 返回值 | 含义 | `cat` 的反应 |
|---|---|---|
| `0` | 文件结束（EOF），**以后也没有了** | 正常退出 ✅ |
| `-EAGAIN` | **暂时**没数据，**以后可能有**（`O_NONBLOCK` 模式） | 报 `Resource temporarily unavailable` 退出 |
| 不返回（阻塞） | 睡着等直到有数据（需等待队列） | 一直等 |

> ⚠️ `-EAGAIN` **不是错误**，是“现在没数据，待会儿再来试试”。
> 本设备缓冲区是固定消息，读完就真没了 → **`return 0` 是正确的**。

**Q2：`copy_to_user` 返回 `5` 是什么意思？**

返回的是**“还剩多少字节没搬完”**（不是错误码！）。
```c
ret = copy_to_user(ubuf, kbuf + pos, count);
/* ret == 0 → 全成功
 * ret == 5 → 有 5 字节没拷成功 → if (ret) return -EFAULT;
 * ❌ 直接 return ret 会让调用者以为“读到了 5 字节”，结论完全反了
 */
```
> 内核里“成功返回什么”**不统一**：`register_chrdev` 成功返回主设备号（正数），`copy_to_user` 成功返回 0。**凭直觉必翻车，必须背 API。**

**Q3：`kmalloc(size, GFP_KERNEL)` 里的 `GFP_KERNEL` 是什么？**

**GFP = Get Free Pages**，是**内存分配的标志位（flags）**，不是地址。

| 标志 | 能睡眠吗 | 用在哪 |
|---|---|---|
| **`GFP_KERNEL`** | ✅ **能睡眠**（内存紧时可回收页缓存/换出 swap） | 进程上下文：`init`/`exit`/`read`/`write`
| **`GFP_ATOMIC`** | ❌ **不能睡眠** | 中断处理函数、自旋锁内部

**为什么中断里不能用 `GFP_KERNEL`**：
```
进程上下文：  task_struct 存在 → 睡了能被唤醒 → 安全 ✅
中断上下文：  该处理程序【不属于任何任务】→ 睡了没人能唤醒它 → 系统死锁 💀
```
内核会用 `BUG: scheduling while atomic` 强制报错。

> **MCU 类比**：`GFP_KERNEL` ≈ 阻塞式发送（可等）；`GFP_ATOMIC` ≈ ISR 里只能读寄存器不能等。
> **铁律：ISR 里绝对不能阻塞** —— 裸机 MCU 和 Linux 内核完全一致。

```bash
sudo cat /dev/edge_ai0         # → Hello from edge_ai_evt module!
```

## 十、第 4 次成果（2026-09-29）✅ `.write` + `.unlocked_ioctl` + 用户态测试程序

### 10.1 工程结构变化：拆出共享头文件

```
drivers/edge_ai_evt/
├── edge_ai_evt.h      ← 契约：命令号 + 结构体 + 常量（内核态【与】用户态共用）
├── edge_ai_evt.c      ← 驱动
├── test_edge_ai.c     ← 用户态测试程序（自写）
├── Makefile
└── README.md
```

```c
// edge_ai_evt.h 的关键结构
#ifdef __KERNEL__
#include <linux/ioctl.h>     /* 内核态 */
#else
#include <sys/ioctl.h>       /* 用户态 */
#endif

#define EDGE_AI_IOC_MAGIC 'E'
#define DEV_NAME    "edge_ai"
#define BUF_SIZE    256

struct edge_ai_put_arg {
    int  len;                /* 数据长度 */
    char data[BUF_SIZE];
};

#define EDGE_AI_IOC_CLEAR  _IO(EDGE_AI_IOC_MAGIC, 0)
#define EDGE_AI_IOC_PUT    _IOW(EDGE_AI_IOC_MAGIC, 1, struct edge_ai_put_arg)
#define EDGE_AI_IOC_LEN    _IOR(EDGE_AI_IOC_MAGIC, 2, int)
```

**为什么必须共享头文件**：命令号是**内核与用户态的契约（ABI）**。两边各写一份，改了一边忘了另一边 → 用户程序发“过时”命令号 → 行为错乱且极难排查。

> `_IO`/`_IOR`/`_IOW` 在内核的 `<linux/ioctl.h>` 和 glibc 的 `<sys/ioctl.h>` 里**定义兼容**，所以同一个头文件两边都能用。

### 10.2 ⭐ 命令号为什么必须编码成“魔数”

不能写 `cmd = 1`、`cmd = 2`。内核提供 4 个宏，因为 `cmd`（`unsigned int`）里**塞了 4 个字段**：

```
 31   30 29 ............ 16 15 14 ............ 8 7 ....... 0
┌─────┬───────────────────┬────────┬────────────────┬──────────┐
│ 方向 │      size         │  type  │                │   nr     │
│(2位)│     (14位)        │ (8位)  │                │  (8位)   │
└─────┴───────────────────┴────────┴────────────────┴──────────┘
```

| 字段 | 作用 |
|---|---|
| **方向** | 数据往哪流（`_IOR` = 驱动→用户，`_IOW` = 用户→驱动） |
| **size** | `datatype` 的大小，用于**校验**（32/64 位兼容） |
| **type**（8 位） | **魔术字**，区分**不同驱动** |
| **nr** | 同驱动内部第几个命令 |

**为什么需要魔术字**：所有驱动的 `ioctl` 共用同一个系统调用入口。如果驱动 A 用 `cmd=1` 表示“清空设备”，驱动 B 也用 `cmd=1` 表示“格式化硬盘”，用户程序**传错 fd** 就造成灾难性误操作。

**`_IOW(..., char *)` 的 size = 8（指针大小）**——这也解释了 **`compat_ioctl` 为何存在**：32 位用户态的指针是 4 字节，size 字段对不上，需要专门转换。

### 10.3 三个命令

| 命令 | 类型 | `arg` 语义 |
|---|---|---|
| `EDGE_AI_IOC_CLEAR` | `_IO` | 无参（`klen = 0`） |
| `EDGE_AI_IOC_PUT` | `_IOW` | 指向 `struct edge_ai_put_arg` 的**用户指针** |
| `EDGE_AI_IOC_LEN` | `_IOR` | 指向 `int` 的**用户指针**，驱动填值 |

### 10.4 ⚠️ `PUT` 的两次迭代（本次最有价值的教训）

**v1（有问题）**：
```c
char user_buf[BUF_SIZE];
copy_from_user(user_buf, (char __user *)arg, BUF_SIZE);   /* ← 无条件拷 256 字节 */
```
**一个“运气型 bug”**：用户传的是 `"Hello from user space!"`（23 字节），驱动却读 256 字节。
- **为什么这次没出错**：字符串字面量在 `.rodata` 段，后面紧跟着别的数据（同页内），恰好都在映射范围 → 成功。**是运气**。
- **何时会炸**：字符串正好落在**页尾**附近时，后面是未映射页 → `copy_from_user` 返回非 0 → 用户看到莫名其妙的 `Bad address`，而且**时灵时不灵**（取决于链接器布局）。**这类 bug 最难查**。

**v2（正确）—— 结构体方案**：
```c
struct edge_ai_put_arg put_arg;
if (copy_from_user(&put_arg, (void __user *)arg, sizeof(put_arg)))   /* 固定大小，契约明确 */
    { ret = -EFAULT; break; }
if (put_arg.len < 0 || put_arg.len > BUF_SIZE)                       /* 长度校验 */
    { ret = -EINVAL; break; }
mutex_lock(&kbuf_lock);
memcpy(kbuf, put_arg.data, put_arg.len);
klen = put_arg.len;
mutex_unlock(&kbuf_lock);
```

**为什么结构体方案优于 `strnlen_user` 方案**：

| | 结构体 | `strnlen_user` |
|---|---|---|
| 接口契约 | ✅ **明确**（传完整 struct） | ⚠️ 隐含（必须 `\0` 结尾） |
| 长度上限 | **由 `len` 字段决定** | 受 `\0` 限制 |
| 能否传**二进制**数据 | ✅ **能**（可含 `\0`） | ❌ 不能 |

> **能传二进制**是决定性的——真实设备（摄像头帧、传感器数据）哪有全是文本的。
> 内核里大量真实驱动就是这么做的（`struct i2c_msg`、`struct v4l2_buffer`）。

> **❗ 长度校验的生死线**：`memcpy` 第三个参数是 `size_t`（无符号）。如果 `len = -1` 通过了校验，
> `memcpy(kbuf, data, (size_t)-1)` 会拷到天荒地老 → **内核堆溢出 → 可被提权**。
> 这正是 `len < 0` 那半边判断存在的理由。

### 10.5 代码 review 要点（本轮新增认知）

| 项 | 结论 |
|---|---|
| ⭐ `_IOC_TYPE(cmd) != MAGIC` **前置检查** | ✅ 用户自己加的，很专业（很多真实驱动都不写）。避免魔术字撞车导致的误操作 |
| 未如的命令返回 **`-ENOTTY`** | ✅ 不是 `-EINVAL`。用户程序靠它区分“命令不支持” vs “参数不合法” |
| `case` 里声明变量 | ⚠️ **`case` 不构成作用域**！实测：**两个 case 都写 `int len;` → `error: redeclaration of 'len' with no linkage`**。要加 `{}` |
| 锁的作用域 | ✅ 只在 `memcpy` 那儿行；`copy_from_user` 在**锁外**（它可能睡眠，**持锁睡眠是内核大忌**） |
| `ssize_t → int` 转 ABI | ✅ `LEN` 用中间变量 `int len = klen`，没有直接拷 `&klen`（64→32 位会语义混乱） |
| `exit` 释放顺序 | ✅ 先断对外入口（device/class/chrdev），后放内部数据（`kfree`）。安全依据：`rmmod` 先检查引用计数，非 0 则直接失败 |

> **实测（板卡上的 GCC 11.4）**：单个 case 里 `int len;` **能编译**（连 `-std=c11 -Werror` 都过）；
> 但两个 case 同名就报 `redeclaration`。→ 说明作用域确实泄漏到了整个 switch 块。

### 10.6 实测结果（✅ 全过）

```
Buffer length: 22                              ← LEN
After CLEAR, buffer length: 0                  ← CLEAR + LEN
PUT succeeded, len = 22                        ← PUT
After PUT, buffer length: 22                   ← LEN
ioctl returned ENOTTY as expected for invalid command
EINVAL as expected for len > BUF_SIZE          ← 边界：超长
EINVAL as expected for len < 0                 ← 边界：负数
```
✅ 内容验证：`sudo cat /dev/edge_ai0` → `Hello from user space!`

> **⚠️ 一个“假 bug”教训**：`cat` 输出**没有换行符**，紧贴在提示符前面，看上去像“没输出”，
> 导致我误判成“驱动和用户态不一致”。**不要用眼睛判断“有没有数据”** —— 用 `wc -c` 数字节、用 `xxd` 看十六进制。
> **为什么没换行**：`klen = strlen(...)` 不含 `\0`，而 `"Hello from user space!"` 本身也没 `\n`。
> **核心概念**：**设备文件不做任何格式化**，`cat` 只把字节**原样搬运**。有没有换行取决于你写进去的内容。
> （MCU 类比：串口发 `"OK"` 而不是 `"OK\r\n"`，上位机就一行连一行。）

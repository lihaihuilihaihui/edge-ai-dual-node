## 一、环境探测（开工前必修课）

### 1.1 板卡上竟然有 12 个 `/dev/video*`

```bash
$ ls -l /dev/video*
crw-rw---- 1 root video 81,  0 Jul 29 21:41 /dev/video0      ← 开机时创建
crw-rw---- 1 root video 81,  1 Jul 29 21:41 /dev/video1
...
crw-rw---- 1 root video 81, 13 Oct  3 11:33 /dev/video10     ← 11:33 才出现！
crw-rw---- 1 root video 81, 14 Oct  3 11:33 /dev/video11
```

### ⭐ 时间戳是铁证

- `Jul 29 21:41` = **板卡启动时刻**（内核枚举所有**内置**设备）
- `Oct 3 11:33` = **插上 USB 摄像头的那一刻**

**为什么可靠**：`/dev` 是 **devtmpfs**（内存文件系统），节点在**设备被驱动认领的瞬间**创建。

> 📌 **实用技巧**：插了新 USB 设备后 `ls -l /dev/xxx` 看时间戳，一眼分辨"哪个是刚插上的"。

### 1.2 三组设备的身份

```bash
$ v4l2-ctl --list-devices
rkisp-statistics (platform: rkisp):           /dev/video8  /dev/video9
rkisp_mainpath (platform:rkisp-vir0):         /dev/video0 ~ /dev/video7  /dev/media0
USB Camera: USB Camera (usb-fd800000.usb-1):  /dev/video10  /dev/video11  /dev/media1
```

| 设备组 | 是什么 | 用得上吗 |
|--------|-------|---------|
| `rkisp_mainpath` → `video0`~`video7` + `media0` | **RK3566 内置 ISP**，处理 **MIPI CSI** 摄像头数据 | ❌ 没接 MIPI 摄像头 |
| `rkisp-statistics` → `video8` `video9` | ISP 的统计信息输出 | ❌ |
| **`USB Camera` → `video10` `video11`** | ✅ **USB 摄像头**（`usb-fd800000.usb-1`） | ✅ **要用的** |

> 💡 **这就是"选 USB UVC、避开 MIPI CSI"的理由的具体体现**：光 RKISP 就占掉 8 个 `video` 节点，而它们对本项目毫无用处。
> 如果一开始走 MIPI 路线，就要面对设备树配置 + ISP 管线 + `media-ctl` 链路配置——风险和工作量都大得多。

### 1.3 ⚠️ 第一个坑：`v4l2-ctl` 默认用 `/dev/video0`

第一次查格式时忘了带 `-d`：

```bash
$ v4l2-ctl --list-formats-ext          # ❌ 没有 -d，默认 /dev/video0
ioctl: VIDIOC_ENUM_FMT
        Type: Video Capture Multiplanar      ← 注意这个词
        [0]: 'UYVY' (UYVY 4:2:2)
        ...
        Size: Stepwise 32x32 - 800x600
```

**这是 `/dev/video0`（MIPI ISP）的格式，不是 USB 摄像头的！**

**这个坑非常阴**：
- 命令**没报错**
- 输出**看起来完全正常**（一堆格式 + 分辨率）
- 你会以为"我的摄像头就这能力"

**教训**：用 `v4l2-ctl` **必须显式 `-d`**，并且**先确认设备身份**。这就是知识库 **K-016「绝不硬编码设备节点」** 的活标本。

> 🔍 **线索**：`Type: Video Capture Multiplanar` —— 这是**多平面**设备。而 USB 摄像头是 `Type: Video Capture`（单平面）。**这个差异后面写代码时至关重要**（决定 `type` 字段填什么）。

### 1.4 ⚠️ 第二个坑：`Capabilities` vs `Device Caps`

```bash
$ v4l2-ctl -d /dev/video10 --info        # 采集节点
        Capabilities     : 0x84a00001    ← Video Capture + Metadata Capture + Streaming
        Device Caps      : 0x04200001    ← Video Capture + Streaming            ← 看这个！

$ v4l2-ctl -d /dev/video11 --info        # 元数据节点
        Capabilities     : 0x84a00001    ← 一模一样
        Device Caps      : 0x04a00000    ← Metadata Capture + Streaming
```

| 字段 | 含义 |
|------|------|
| `Capabilities` | **整个驱动**的能力 |
| **`Device Caps`**（`device_caps`） | **这个具体节点**的能力 ← **判断依据** |

**两个节点的 `Capabilities` 完全相同，但 `Device Caps` 不同。只读 `Capabilities` 会误判。**

> **为什么 UVC 摄像头有两个节点**：一个出**视频流**（`video10`），一个出**元数据**（`video11`，UVC 标准里的附加信息）。
> 写代码时必须用 `device_caps` 判断，或者至少按 `v4l2-ctl --list-devices` 里的节点顺序人工确认。

### 1.5 摄像头真实能力（`-d /dev/video10`）

```
[0]: 'MJPG' (Motion-JPEG, compressed)
        Size: Discrete 1600x1200    Interval: Discrete 0.033s (30.000 fps)
        Size: Discrete 1280x720     Interval: Discrete 0.033s (30.000 fps)
        Size: Discrete 640x480      Interval: Discrete 0.033s (30.000 fps)
[1]: 'YUYV' (YUYV 4:2:2)
        Size: Discrete 1600x1200    Interval: Discrete 0.200s ( 5.000 fps)
        Size: Discrete 1280x720     Interval: Discrete 0.100s (10.000 fps)
        Size: Discrete 640x480      Interval: Discrete 0.033s (30.000 fps)
```

**有 MJPG** ✅ → 帧数据本身就是 JPEG，**存文件 = 直接写字节，零转码**。

### 1.6 ⭐ 算一遍带宽，就明白为什么高分辨率 YUYV 帧率暴跌

**YUYV 未压缩，每像素 2 字节**：

| 分辨率 | 每帧大小 | 帧率 | **带宽** |
|--------|---------|------|---------|
| 640×480 | 640×480×2 = **600 KB** | 30 fps | **18.4 MB/s** |
| 1280×720 | 1280×720×2 = **1.8 MB** | 10 fps | **18.4 MB/s** |
| 1600×1200 | 1600×1200×2 = **3.7 MB** | 5 fps | **19.2 MB/s** |

**三行带宽几乎一样（~18-19 MB/s）——这不是巧合**：

- USB 2.0 理论 480 Mbps = 60 MB/s
- 扣掉协议开销，**等时传输（isochronous）** 可用约 35~40 MB/s
- UVC 驱动留余量后压到 **~19 MB/s**
- 摄像头想发更多？**总线不答应** → 驱动只能**降帧率**

**MJPG 是压缩的**（JPEG 压缩比 1/10 ~ 1/20）：

| 分辨率 | 每帧约 | 帧率 | 带宽 |
|--------|-------|------|------|
| 640×480 | ~55 KB（**实测 54.7 KB**） | 30 fps | **~1.6 MB/s** |
| 1280×720 | ~100 KB | 30 fps | ~3 MB/s |
| 1600×1200 | ~200 KB | 30 fps | ~6 MB/s |

**压缩 11 倍（实测）→ 带宽富余 → 全分辨率都能 30fps。**

> ✅ **结论：用 MJPG。** 本项目选 640×480 MJPG 30fps：
> - 带宽仅 1.64 MB/s（USB 预算的 8%）
> - 帧数据直接就是 JPEG，存文件零转码
> - 640×480 也接近阶段 3 推理需要的 640×640

## 二、核心原理：V4L2 的"借还"模型

### 2.1 V4L2 本质上还是字符设备

`/dev/video10` 也是字符设备（major 81）。区别在于：**它的 `ioctl` 命令是标准化的**（`VIDIOC_*`），所有摄像头遵守同一套协议。

> **MCU 类比**：你在 STM32 上写 DCMI 驱动，寄存器是 ST 定的；换芯片寄存器全变。
> V4L2 相当于"**全行业统一的摄像头寄存器手册**"——不管哪家摄像头，`VIDIOC_S_FMT` 就是设格式、`VIDIOC_DQBUF` 就是取一帧。

### 2.2 为什么不能直接 `read()` 取帧？

**可以**，V4L2 支持 `read()` 方式。**但性能很差**：内核要把每帧数据**拷一份**到用户空间。

算一下：640×480 YUYV 一帧 600 KB，30fps → **每秒拷 18MB**，CPU 全耗在拷贝上。

**所以现代做法是 `mmap`**：内核分配缓冲区，用户态把它**映射进自己的地址空间**，驱动直接往里写 → **零拷贝**。

> **MCU 类比**：这正是 **DMA + 多缓冲**。不用 DMA 就得 CPU 自己搬每个字节（≈`read()`）；用 DMA，外设直接写内存（≈`mmap`）。

### 2.3 ⭐ 队列模型 = "空桶传送带"

```
        驱动侧                                      用户侧
   ┌──────────────┐                          ┌──────────────┐
   │  4 个 buffer │                          │              │
   │  B0 B1 B2 B3 │  ← 内核分配 + mmap 映射 →  │  都在你的地址空间 │
   └──────────────┘                          └──────────────┘

   QBUF(B0..B3)  →  把 4 个【空桶】放上传送带（"这些你可以装"）
   STREAMON      →  开机，传送带转起来；驱动一边采集一边往桶里装水
   DQBUF         →  从完成端拿走一个【装满的桶】（会阻塞，直到有）
                    此时该 buffer 归【用户】，驱动不会碰它
   处理数据      →  存 JPEG / 送去推理
   QBUF          →  倒空桶，重新放回传送带（还回去！）
                    循环往复……
```

**必须想清楚的三个点**：

| 问题 | 答案 |
|------|------|
| **为什么要 4 个 buffer？** | 只有 1 个时：驱动装水时你不能取，你取时驱动不能装 → 交替空等、狂丢帧。4 个才能形成**流水线** |
| **`DQBUF` 拿到的 buffer 归谁？** | **归你**。驱动在你 `QBUF` 还回去之前**不会碰它**，所以你可以慢慢处理 |
| **忘了 `QBUF` 会怎样？** | 传送带上桶越来越少 → 全部耗尽后驱动采不到数据 → `DQBUF` **永远阻塞、画面卡死**。**这是 V4L2 最经典的 bug** |

> **MCU 类比（精确版）**：
>
> | V4L2 | 裸机 DMA |
> |------|---------|
> | `QBUF` | 把缓冲区地址写进 DMA 描述符链，启动传输 |
> | 驱动填数据 | DMA 搬运 |
> | `DQBUF` | 传输完成中断里"取走已填好的缓冲区" |
> | 用完 `QBUF` | 清空缓冲区，重新挂回描述符链 |
> | 忘了 `QBUF` | 描述符链耗尽 → DMA 停了、画面卡住 |
>
> **唯一区别**：Linux 里"通知"是**应用主动 `DQBUF` 阻塞等**，而不是中断回调。

### 2.4 完整 ioctl 序列

```
 1. open("/dev/video10", O_RDWR)
 2. VIDIOC_QUERYCAP     查设备能力（看 device_caps 有没有 VIDEO_CAPTURE）
 3. VIDIOC_S_FMT        请求格式（分辨率 + 像素格式）    ← 传入传出！
 4. VIDIOC_G_FMT        读回实际生效格式（或用 S_FMT 的回填值）
 5. VIDIOC_REQBUFS      申请 N 个 buffer              ← count 也是传入传出！
 6. VIDIOC_QUERYBUF ×N  查每个 buffer 的 length / offset
 7. mmap() ×N           映射到用户空间
 8. VIDIOC_QBUF ×N      全部入队
 9. VIDIOC_STREAMON     开始采集
10. VIDIOC_DQBUF        取一帧  ← 循环体
11. 处理数据
12. VIDIOC_QBUF         还回去
13. VIDIOC_STREAMOFF    停止采集
14. munmap() ×N
15. close()
```

### 2.5 ⚠️ 三个经典陷阱

#### 陷阱 1：`bytesused` ≠ `length`

`VIDIOC_DQBUF` 回来后，`struct v4l2_buffer` 里有两个长度字段：

| 字段 | 含义 | 写文件用哪个 |
|------|------|-------------|
| `length` | buffer 的**总容量** | ❌ |
| **`bytesused`** | **这一帧实际有效数据的字节数** | ✅ **必须用这个** |

**实测证据**：

```
buffer[0]: length=614400        ← 614400 = 640×480×2（按【未压缩】尺寸分配）
DQBUF:     bytesused=54716      ← 实际帧只有 54.7 KB
```

**为什么 `length` 是未压缩尺寸**：UVC 驱动按"**最大可能的帧大小**"保守分配，保证万一格式被换成 YUYV 也装得下。

**用 `length` 写文件会怎样**：写出 614400 字节，其中 **559684 字节是垃圾**（buffer 里没被填的残留数据）→ 文件大概率打不开。

#### 陷阱 2：`type` 必须选对（单平面 vs 多平面）

| 类型 | 何时用 |
|------|-------|
| `V4L2_BUF_TYPE_VIDEO_CAPTURE` | **单平面** ← USB 摄像头用这个 |
| `V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE` | 多平面（如 RKISP） |

**怎么判断**：看 `--list-formats-ext` 输出里的 `Type:` 字段。

> 这就是 1.3 第一个坑的"伏笔回收"：`/dev/video0` 是 `Multiplanar`，`/dev/video10` 是 `Capture`。
> **type 用错的话，后面所有 ioctl 全部失败。**

#### 陷阱 3：`S_FMT` 和 `REQBUFS` 都是"传入传出"

**驱动不保证接受你的请求**（不支持的分辨率可能被四舍五入、不支持的格式可能被换掉）。

```c
req.count = 4;                       /* 输入：我想要 4 个 */
ioctl(fd, VIDIOC_REQBUFS, &req);
for (i = 0; i < req.count; i++) { }  /* ✅ 用返回后的 count，不是写死的 4 */

ioctl(fd, VIDIOC_S_FMT, &fmt);       /* 驱动会把【实际生效值】回填到 fmt 里 */
printf("%ux%u\n", fmt.fmt.pix.width, fmt.fmt.pix.height);   /* ← 这是实际值，不是你的请求！ */
```

**铁律**：用**返回后的实际值**算后续逻辑（尤其是 buffer 大小）。

> **嵌入式通用规律**：凡是你"请求"的东西，都要**读回确认实际值**——和串口波特率、时钟树配置一个道理。

## 三、实战

### 3.1 热身：`v4l2-ctl` 一把梭（先验证链路）

```bash
cd ~/edge-ai-dual-node/stage1-rk3566/apps/v4l2-capture

v4l2-ctl -d /dev/video10 \
  --set-fmt-video=width=640,height=480,pixelformat=MJPG \
  --stream-mmap --stream-count=1 --stream-to=frame.jpg

file frame.jpg      # → JPEG image data, 640x480
```

**为什么值得先做这一步**：确认"摄像头 → 驱动 → mmap → 文件"整条链路是通的。
后面自己写的代码万一失败，可以**直接排除硬件/驱动层**（**分层定位**，阶段 0 学的排错法）。

> `--stream-mmap` 就是"用 mmap + 队列"的方式抓帧 —— **自己写的程序就是它的展开版**。

### 3.2 自己写 `capture.c`

**文件**：`apps/v4l2-capture/capture.c`（约 200 行）

**核心结构**：

```c
struct buffer {
    void  *start;     /* mmap 返回地址 */
    size_t length;    /* buffer 容量（来自 QUERYBUF） */
};
```

**关键代码片段**：

```c
/* 4. 读回实际格式，并确认真的是 MJPG */
ioctl(fd, VIDIOC_G_FMT, &fmt);
if (fmt.fmt.pix.pixelformat != V4L2_PIX_FMT_MJPEG) {
    fprintf(stderr, "驱动没有给 MJPG!\n");
    goto cleanup;
}

/* 5. 申请 buffer —— 用返回后的 count */
req.count = 4;
req.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
req.memory = V4L2_MEMORY_MMAP;
ioctl(fd, VIDIOC_REQBUFS, &req);
if (req.count < 2) { /* 不够用，退出 */ }

buffers = calloc(req.count, sizeof(*buffers));

/* 6. 查询 + mmap */
for (i = 0; i < req.count; i++) {
    buf.type = ...; buf.memory = ...; buf.index = i;
    ioctl(fd, VIDIOC_QUERYBUF, &buf);
    buffers[i].length = buf.length;
    buffers[i].start  = mmap(NULL, buf.length, PROT_READ | PROT_WRITE,
                             MAP_SHARED, fd, buf.m.offset);
    if (buffers[i].start == MAP_FAILED) { ... }   /* ⚠️ 不是判 NULL */
}

/* 9~12. 取一帧并写文件 */
ioctl(fd, VIDIOC_DQBUF, &buf);
fwrite(buffers[buf.index].start, 1, buf.bytesused, fp);   /* ⚠️ bytesused! */
ioctl(fd, VIDIOC_QBUF, &buf);                             /* 还回去 */
```

### 3.4 ⭐ 数据解读（三个教学点）

#### ① `length=614400` = 640×480×2

**MJPG 格式下，buffer 却按 YUYV 的尺寸分配** → 印证了"驱动按最大可能帧大小保守分配"。

#### ② `bytesused=54716` → 压缩比 11.2 倍

`614400 ÷ 54716 ≈ 11.2` —— 落在"JPEG 典型压缩比 1/10~1/20"区间 ✅

#### ③ 带宽实测 vs 预测

```
54716 字节 × 30 fps ≈ 1.64 MB/s
```

**预测 ~1.5 MB/s → 实测 1.64 MB/s，吻合** ✅

| | 每帧 | 30fps 带宽 |
|---|---|---|
| **MJPG（实测）** | 54.7 KB | **1.64 MB/s** |
| YUYV（理论） | 600 KB | 18.4 MB/s |
| | | **相差 11 倍** |

**USB 2.0 的 ~19 MB/s 预算，MJPG 只吃掉 1.64 MB/s（8%）** → 高分辨率也绰绰有余。

#### ④ mmap 地址递减（附带观察）

```
offset 递增：0 → 614400 → 1228800 → 1843200
mmap 地址递减：0x7f85eaa000 → 0x7f85e14000 → 0x7f85d7e000 → 0x7f85ce8000
```

**两者无关**：
- `offset` 是**设备侧**的偏移（驱动指定的 buffer 布局）
- `mmap` 返回的地址是**内核选的用户态虚拟地址**（通常从高往低分配，所以递减）

相邻地址差值都是 `0x96000 = 614400` —— 说明这些映射**紧紧相邻**（逆序排列）。

> **概念**：`mmap(addr, len, prot, MAP_SHARED, fd, offset)` 的语义是"**把 fd 的 offset 处的 len 字节映射到某块虚拟地址**"，映射到哪由内核决定。

## 四、代码 review 要点

### 做得好的（超出预期）

| 项 | 为什么重要 |
|----|-----------|
| ⭐ **`buffers[buf.index]`** | **没有硬编码 `[0]`**。`DQBUF` 回来的 index 由驱动给，**不能假设总是 0** |
| ⭐ **`buf.bytesused`** | 用了正确字段（见 §2.5 陷阱 1） |
| **`MAP_FAILED` 判断** | `mmap` 失败返回 `MAP_FAILED` 不是 `NULL`；cleanup 里也一起挡了 |
| **`req.count < 2` 防护 + 用返回后的 count** | 没有盲信自己的请求 |
| **`G_FMT` 后检查 pixelformat** | 驱动可能悄悄换成 YUYV；主动检查而不是盲信 |
| **fourcc 用位运算拆字节** | 不依赖主机字节序 |
| **完整错误处理 + `goto` 统一清理** | 和 1.2 内核驱动风格一致 |

### 改进项（已改）

#### ⚠️ `DQBUF` 之后出错必须 `goto requeue`（不是 `goto cleanup`）

**问题**：`DQBUF` 之后 buffer 的**归属权已转移到用户**。此时若 `goto cleanup` 直接走人，就是"**借了东西没还**"。

```c
ioctl(fd, VIDIOC_DQBUF, &buf);
fp = fopen(OUT_FILE, "wb");
if (!fp) {
    perror("fopen");
    goto requeue;        /* ✅ 先还 buffer，再清理 —— 不能 goto cleanup */
}
```

**为什么必须**：
- 单帧场景下，`close(fd)` 会让内核强制回收所有 buffer（V4L2 规范保证），**不会崩**
- 但如果代码演变成"**抓多帧**"，buffer 泄漏会直接导致**采集卡死**（§2.3 的"桶全用完"）

**规则**：**`DQBUF` 和 `QBUF` 之间的所有错误路径，都必须先还 buffer 再清理。**

> 编译器用 `-Wunused-label` 提醒了这个问题 —— **用户的"意图"是对的，只是没接上线**。

#### `S_FMT` 打印的标签要准确

`VIDIOC_S_FMT` 是**传入传出**的，调用后结构体里已经是**实际值**。

要打印"请求值"，得在调用前存一份副本；或直接打印字面量（已改为此法）。

## 一、本次完成的功能

### 1.1 运行时枚举设备节点（落实 K-016）

把硬编码的 `#define DEV_NAME "/dev/video10"` 换成 `find_capture_device()`。

**筛选条件（三个都要满足）**：

| 条件 | 代码 |
|------|------|
| 是 UVC 驱动 | `strcmp((const char *)cap.driver, "uvcvideo") == 0` |
| **能采集视频** | `cap.device_caps & V4L2_CAP_VIDEO_CAPTURE` |
| 支持流式 I/O | `cap.device_caps & V4L2_CAP_STREAMING` |

**为什么三个都要**：
- 只查 `VIDEO_CAPTURE` → 可能选中 RKISP 的节点（`video0`~`video9`）
- 只查 `driver` 名 → 会选中 `video11`（也是 `uvcvideo`，但是 metadata 节点，**没有 `VIDEO_CAPTURE`**）

> ⚠️ **注意区分"能力"和"身份"**：
> - **能力**（`device_caps`）回答"这个节点能干什么"
> - **身份**（`driver` 名）回答"它是谁"
>
> 两者都要查。`video10` vs `video11` 就是靠 `device_caps` 区分开的（K-041）。

**实现要点**：

```c
/* 遍历 /dev/video0 .. /dev/video63 */
int fd = open(path, O_RDWR);
if (fd < 0) {
    if (errno == ENOENT) continue;      /* 没这个节点 → 正常，下一个 */
    fprintf(stderr, "打开 %s 失败: %s\n", path, strerror(errno));   /* 权限等 → 要报出来 */
    continue;
}
ioctl(fd, VIDIOC_QUERYCAP, &cap);
/* 三个条件都满足 → snprintf(node, len, "%s", path); close(fd); return 0; */
close(fd);      /* ⚠️ 匹配成功的那次也要 close（只是探测，后面会重新 open） */
```

**又学到两点**：

| 坑 | 说明 |
|----|------|
| **`cap.driver` 是 `__u8[16]`，不是 `char *`** | 直接传给 `strcmp` 会有 `incompatible pointer type` 警告 → 要 `(const char *)cap.driver` 强转 |
| **`open` 失败不能一律 `continue`** | 要区分 `ENOENT`（节点不存在，正常）和 `EACCES`（权限不足，**要报出来**）—— 否则"找不到设备"的真实原因被静默吞掉 |

**实测输出**：

```
[0] 找到采集设备: /dev/video10, fd=4
```

### 1.2 连续采集循环

```c
/* STREAMON 之后 */
for (i = 0; i < total_frames; i++) {
    DQBUF                       /* 取一帧 */
    frames_ok++;
    total_bytes += buf.bytesused;

    if (i == 0) 保存第一帧        /* 只存一帧，避免磁盘 IO 干扰 FPS */
    if ((i+1) % 10 == 0) printf  /* 每 10 帧报进度 */

    QBUF                        /* ⭐ 还回去 */
}
```

**两个刻意的设计**（都是用户自己想到的，很好）：
- **只保存第一帧** —— 避免 `fwrite` 的磁盘 IO 干扰 FPS 测量
- **预热 5 帧后再开始计时** —— 躲开 UVC 预热期（K-020）

### 1.3 FPS 计时

```c
static double now_sec(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);   /* ✅ 单调时钟，不受 NTP 影响 */
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

double t_start = now_sec();     /* 在循环【之前】 */
for (...) { ... }
double t_end = now_sec();

printf("总耗时 : %.3f 秒\n", t_end - t_start);
printf("平均 FPS : %.2f\n", frames_ok / (t_end - t_start));
```

> **为什么必须用 `CLOCK_MONOTONIC`**：`CLOCK_REALTIME` 会被 NTP 校正往回拨，可能算出**负的时间差**。
> **MCU 类比**：单调时钟 ≈ **SysTick 计数器**（只增不减）；`REALTIME` ≈ **RTC**（人类时间，可被改写）。**测时间间隔永远用单调时钟。**

### 2.2 ⭐ 最强怀疑：自动曝光把帧率拖下来了

**曝光时间和帧率直接挂钩**（最长曝光时间不能超过帧间隔）：

| 曝光时间 | 理论帧率上限 | 对应观察 |
|---------|-------------|---------|
| **31.2 ms** | `1/0.0312 ≈ 32 fps` | ← `hardware.md` 记录的 `exposure_time_absolute = 312`，正是 09-10 白天测到 **30.23 fps** 的原因 |
| **60 ms** | `1/0.060 ≈ 16.6 fps` | ← **正好对上本次的 16.58 fps！** |

**推理链**：
1. USB 摄像头默认跑自动曝光（`hardware.md`：`auto_exposure=3` Aperture Priority）
2. **光线暗 → 自动曝光自动拉长曝光时间 → 帧率被拖下来**
3. 本次是**晚上**测的；30.23fps 那次是 **09-10 白天**测的

**两个旁证**：
- 平均帧 44.7 KB vs 昨天 54.7 KB —— 暗画面噪声少、平坦区域多，**JPEG 压得更小** ✅
- `16.58 fps → 60ms 曝光` 与 `30.23 fps → 31ms 曝光` 的对应关系**非常整齐**，不像巧合

> ⚠️ **这是假设，不是结论。** 但它可验证，且验证成本极低。

## 二补、⭐ 结论：FPS 与丢帧（2026-10-05 实测闭环）

### 2b.1 第一轮假设：自动曝光（方向对，但验证方法有缺陷）

| 观察 | 数字 |
|------|------|
| 首次实测 | 16.58 fps → 每帧 60.3 ms |
| `hardware.md` 记录（09-10 白天） | 30.23 fps → 每帧 33.0 ms |
| `hardware.md` 记录曝光 | `exposure_time_absolute = 312`（31.2 ms） |

**推理**：曝光时间不能超过帧间隔 → `31.2ms → 上限 32fps`（对上 30.23）；`60ms → 上限 16.6fps`（对上 16.58）。

**假设**：晚上光线暗 → 自动曝光拉长到 ~60ms → 帧率被物理限制住。

**⚠️ 我的验证方法有缺陷**：我让用户"**现在**查曝光值"，得到 312 —— 但这是"**现在**"的状态，**不是"16.58 那次"的**。

**正确做法 —— 测量前后各采一次状态**：

```bash
v4l2-ctl -d /dev/video10 --get-ctrl=exposure_time_absolute,auto_exposure,gain   # 测之前
./capture 100
v4l2-ctl -d /dev/video10 --get-ctrl=exposure_time_absolute,auto_exposure,gain   # 测之后
```

> **教训（K-046 补强）**：摄像头这类**自适应设备**（自动曝光/增益/对焦），同一份代码会跑出不同结果。
> **性能数据必须连同"测试条件"一起记录，且条件要在测量前后各采一次。**

### 2b.2 转折：同一份代码，重跑得到 30.23 fps

用户**未改任何代码**重跑一次：

```
总耗时       : 3.308 秒
平均 FPS     : 30.23
平均每帧大小 : 29969.1 字节
```

**与 `hardware.md` 记录的 30.23 一字不差。**

| | 第一次 | 第二次 |
|---|---|---|
| FPS | 16.58 | **30.23** |
| 平均帧大小 | 44.7 KB | **30.0 KB** |

**帧大小是"噪声的指纹"**：暗光下摄像头必须提高增益 → 噪声增加 → 高频细节多 → **JPEG 压不小**（虽然画面"内容"少）。

**结论**：**16.58 那次是暗光下的物理上限，不是 bug。** 环境变了，数字就变了。

> 至此"FPS 异常"**闭环**：代码没问题，是测试条件差异。

### 2b.3 ⭐ 重头戏：buffer 周转实验（含我的第二次误判）

30fps 已达标，正常路径无性能问题。但"**消费者慢会怎样**"这个知识在真实应用里必须懂（AI 推理一定跟不上 30fps）。

**实验设计**：加可控延时，扫 `delay = 0 / 20 / 30 / 40 / 60 / 100 / 200 ms`，观察 FPS 与丢帧。

#### 我最初给的理论模型

| 符号 | 含义 |
|------|------|
| **H** | 你**持有 buffer** 的时间（`DQBUF` → `QBUF`） |
| **T** | 帧间隔 = 33 ms |

```
H < T → 处理完要【等】下一帧 → 不丢帧，FPS = 30
H > T → 队列积压、驱动丢帧   → 丢帧率 = 1 − T/H
```

#### ⚠️ 中途误判：我以为发现了 "flow control"

第一轮扫描的结果里，**"平均帧间隔"竟然跟着 delay 变**（40ms→39.4ms、100ms→97.9ms、200ms→194.9ms），而**"丢帧率"稳定在 ~3%**。

**我据此推断**："UVC 驱动有 flow control，会暂停摄像头，所以不丢帧、只是降速。"

**这个推断是错的。**

#### ⭐ 转折：用 `sequence` 一锤定音

让用户打印 `buf.sequence`（内核累加的帧序号），跑 `delay = 200ms`：

```
seq=6  ts=14368.341559
seq=7  ts=14368.377395
seq=8  ts=14368.409549
seq=9  ts=14368.441496
seq=14 ts=14368.609417    ← 跳到 14！中间 10~13 被丢了
seq=20 ts=14368.805492    ← 每步 +6
seq=26 ts=14369.005596
...
```

**`sequence` 跳跃 → 确实在丢帧。**

**那我为什么会误判？答案在"指标选错了"**：

| 字段 | 反映什么 | 会被"读法"污染吗 |
|------|---------|----------------|
| `timestamp` 的**间隔** | **你拿到的**相邻帧隔了多久（**里面含丢掉的帧**） | ⚠️ **会** |
| **`sequence`** | **摄像头一共出了多少帧**（内核逐一累加，与你怎么读无关） | ✅ **不会** |

**"时间戳间隔 ≈ delay"根本不需要 flow control 解释**：两次 `DQBUF` 之间摄像头走了 6 帧，时间戳自然跳 `6 × 33ms = 198ms ≈ 200ms`。就这么简单。

> **教训（K-048）**：**选指标要选"不会被观测方式污染"的那个。**
> `sequence` 是内核累加的**绝对量**；`timestamp` 的**间隔**取决于**你何时去取**。
> 用错指标 → 推出完全错误的理论。

#### 用对的指标重测：曲线被精确验证

修正统计公式（用 `sequence` 跨度算真实帧率）后重跑：

| delay | 程序 FPS | **真实帧率** | **丢帧率** | 理论 `1 − T/H` |
|-------|---------|-------------|-----------|---------------|
| 0 | 30.23 | **30.22** | **0.0%** | 0% |
| 20 ms | 30.05 | **30.22** | **0.0%** | 0% |
| 30 ms | 29.96 | **30.22** | **0.0%** | 0% |
| **40 ms** | 24.63 | **30.22** | **16.0%** | 17.3% |
| **60 ms** | 16.49 | **30.22** | **43.5%** | 44.8% |
| **100 ms** | 9.94 | **30.21** | **65.9%** | 66.9% |
| **200 ms** | 4.98 | **30.23** | **82.9%** | 83.5% |

**三个关键结论**：

1. **"真实帧率"始终 30.2 fps** —— 摄像头一直满速跑，**丢的是消费者**
2. **丢帧率精确跟随 `1 − T/H`**（误差 < 1.5%）
3. **临界点 `H = T = 33ms` 被精确定位**：30ms → 0%，40ms → 16%（**斜率极陡，没有温柔过渡**）

**那 1% 的差值是什么？—— "存货效应"**：

```
摄像头出帧数 = 4（buffer 存货） + (程序取到的帧数 − 4) × H / T
```

| delay | 模型预测 | 实测 |
|-------|---------|------|
| 40 ms | `4 + 96×40/33.09 = 120` | **119** ✅ |
| 60 ms | `4 + 96×60/33.09 = 178` | **177** ✅ |
| 100 ms | `4 + 96×100/33.09 = 294` | **293** ✅ |
| 200 ms | `4 + 96×200/33.09 = **584**` | **584** ✅ **完全吻合** |

> **"4 个 buffer = 4 帧存货"这个推断，被数据钉死了。**
> 也解释了为什么启动时前 4 次 `DQBUF` 不用等（`seq=6,7,8,9` 连续）。

### 2b.4 最终结论表

| 结论 | 状态 |
|------|------|
| `H < T` 不丢帧；`H > T` 丢帧率 = `1 − T/H` | ✅ 实测误差 < 1.5% |
| 临界点 = 帧间隔 = 33 ms | ✅ 精确定位 |
| 4 个 buffer = **4 帧存货 + 132ms 抗抖动余量** | ✅ 吻合到 0.2% |
| 真实帧率与消费者无关，恒为 30.2 fps | ✅ 全表一致 |
| **UVC 不提供 flow control**（消费者慢就是丢帧） | ✅ `sequence` 证明 |
| **加 buffer 不能解决"持续不匹配"** | ✅ 理论 + 实测 |

## 二补.5、对后续开发的影响（重要）

### ① 阶段 3 的推理时间**硬预算 = 33 ms**

```
YOLOv8n INT8 @ 640×640 在 RK3566 NPU（~1 TOPS）：很可能 50~150 ms/帧
```

用上面的实测曲线外推：

| 推理耗时 H | 丢帧率 | 实际可用帧率 |
|-----------|--------|------------|
| 33 ms | 0% | 30 fps |
| 50 ms | **33%** | 20 fps |
| 100 ms | **67%** | 10 fps |
| 150 ms | **78%** | 6.7 fps |

**→ 推理不可能每帧都做。这不是"优化问题"，是"架构问题"。**

### ② 两种应对策略：**降帧率** 优于 **抽帧**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **抽帧**（现在的丢帧） | 摄像头照常 30fps，只取 1/3 | 拿到的都是**新**帧，延迟低 | **USB 一直满速传**，白耗带宽/功耗 |
| **降帧率** ⭐ | `VIDIOC_S_PARM` 设 `timeperframe`，让摄像头只出 10fps | **省 USB 带宽、省功耗** | 需改摄像头参数；帧间隔变长 |

> **本项目"低功耗边缘节点"是核心卖点** → **应优先考虑 `VIDIOC_S_PARM`**。
> 30fps → 10fps 可使 USB 传输量降到 1/3，板卡与 USB 子系统功耗都下降。
> 📌 留到阶段 3 做功耗优化时实施。

### ③ ⚠️ "加 buffer"不是解决方案

```
加 buffer（4 → 16）→ 只是把【存货】从 4 帧变成 16 帧
                    → 稳态丢帧率【一模一样】（还是 1 − T/H）
                    → 代价：延迟更大（队列压了更多旧帧）
```

**加 buffer 只能抗"抖动"，不能治"持续不匹配"。**
治本只有两条：**降生产者速度** 或 **降消费者频率**。

### ④ ⭐ 低延迟取帧模式（阶段 3 要用）

**队列积压 = 延迟**。`delay=200ms` 时队列里始终压着几帧 → 拿到的画面比"当前"旧 100~200ms。

**对照 `SPEC.md`**：`端到端延迟（PIR→蜂鸣器）稳态 < 800ms` —— 每环都要省时间。

**低延迟取帧的标准写法**（主动丢弃旧帧，只处理最新的）：

```c
/* 拿一帧，然后把队列里积压的旧帧全部丢掉，只留最新的 */
ioctl(fd, VIDIOC_DQBUF, &buf);
while (ioctl(fd, VIDIOC_DQBUF, &buf2) == 0) {   /* 需配合 O_NONBLOCK 或 poll 超时 0 */
    ioctl(fd, VIDIOC_QBUF, &buf);                /* 把旧的还回去（= 丢弃） */
    buf = buf2;                                  /* 保留更新的 */
}
/* 此时 buf 是"当前最新"帧 → 处理它 → 延迟最低 */
```

> 这才是"快速周转"的**真正用法**：不是防丢帧，而是"**永远处理最新帧**"。

## 一、这一节解决什么问题

**环境问题会伪装成代码 bug。** 摄像头打不开，你以为是 V4L2 用错了，其实是没权限。
先把「谁能访问哪些设备」这层搞清楚，后面写驱动/采集时就不会在错误的地方找原因。

对比 MCU：你在 STM32 里直接操作寄存器，**没有权限这一层**——因为 MCU 上"能跑代码 = 有权限"。
Linux 把「能不能访问某个资源」和「程序逻辑对不对」拆成了两件独立的事，这是多用户操作系统的必然代价。

## 二、核心原理

### 2.1 权限位三段结构

```
crw-rw---- 1 root video 81, 13 /dev/video10
│└┬┘└┬┘└┬┘   │    │
│ │  │  │    │    └─ 属组（group）
│ │  │  │    └────── 属主（owner）
│ │  │  └─────────── other 的权限位
│ │  └────────────── 属组的权限位
│ └───────────────── 属主的权限位
└─────────────────── 文件类型（b/c/d/l/s/p/-）
```

### 2.2 判断规则：命中即停（关键）

> 内核按 **属主 → 属组 → other** 的顺序，用 UID/GID **先确定你属于哪一类身份**，
> 然后**只应用那一类的 3 个权限位**。一旦命中就不再往后看，**也不取最宽松的那个**。

**实测验证（三步表）**——文件权限固定 `004`（`-------r--`，只有 other 可读）：

| 步骤 | 属主 | 属组 | 实验者 `lihaihui`(1001) 的身份 | 内核看哪段 | 结果 |
|---|---|---|---|---|---|
| ① | `lihaihui` | sudo | 属主 | 第 1 段 `---` | ❌ 拒绝 |
| ② | `lckfb` | sudo | **属组**（在 sudo 组） | **第 2 段 `---`** | **❌ 拒绝** |
| ③ | `lckfb` | `lckfb` | other | 第 3 段 `r--` | ✅ 成功 |

**第 ② 格是全部价值所在**：other 段明明写着 `r--`，但因为身份在属组段就命中了，
内核**根本不会去看 other 段**。这就是"命中即停、不取最大权限"。

> 💡 反直觉结论：`chmod 004` 这种「把属主和属组都关死」的权限，反而让**外人**成了唯一能读的人。
> 现实中 `000`/`004` 常用于**保护文件防误改**——日常改不动，必须显式 `sudo`，等于一道手动确认。

### 2.3 几个必须记牢的点

| 点 | 说明 |
|---|---|
| 比对的是**数字**，不是名字 | 内核比 `euid` vs 文件 `uid`；`ls -l` 显示的用户名只是翻译 |
| 属组判断含**附加组** | 你的 `groups` 列表里所有组都算 |
| `usermod` 后必须**重新登录** | 改的是 `/etc/group` **文件**，改不了已运行进程内核里的 `struct cred` |
| **不要用 sudo 做日常开发** | 产物属主变 root，之后非 sudo 改不了、编译输入输出混乱 |

### 2.4 主设备号 / 次设备号

- **主设备号 → 驱动**（一个主号只对应一个驱动）
- **次设备号 → 该驱动下的设备实例**
- ⚠️ **设备文件名里的数字 ≠ 次设备号**

实测：`/dev/video10` 是 `81:13`（不是 `81:10`），因为中间被 `v4l-subdev0~2` 占了 `81:10~12`。
串口更明显：`ttyS1` = `65`、`ttyS3` = `67`（8250 驱动惯例 `次号 = 64 + 端口号`）。

次设备号只能从 `ls -l` 或 `/sys/class/<子系统>/<设备>/dev` **读**，不可从文件名推断。

### 2.5 设备节点与用户组（本项目实测）

| 节点 | 属组 | 缺了会怎样 | 状态 |
|---|---|---|---|
| `/dev/video*`、`/dev/mpp_service`、`/dev/rga` | `video` | 摄像头打不开 | ✅ 已加入 |
| `/dev/dri/renderD*` | `render` | NPU 推理失败 | ✅ 已加入 |
| `/dev/ttyS*` | **`dialout`**（不是 `tty`） | 串口打不开 | ✅ 已加入 |

## 三、踩的坑

### 坑 1：`sudo` 也写不进 `/tmp` 里别人的文件（→ K-024）

在 `/tmp` 做权限实验时，`sudo sh -c 'echo SECRET > /tmp/perm-lab.txt'` 报 `Permission denied`。
诡异点：**root 身份 + 文件权限 666 全开**，仍然被拒。

**根因**：两道机制叠加
1. `/tmp` 是 sticky 目录（`drwxrwxrwt` 结尾的 `t`）
2. `fs.protected_regular = 2`（Ubuntu 22.04 默认）

内核在 sticky 目录里 `open(O_CREAT)` 一个**已存在且属主不是自己**的普通文件时直接 `EACCES`：
**不走权限位**（666 无效）、**不受 `CAP_DAC_OVERRIDE` 豁免**（root 也拦）。

**控制变量实测**：

| 目录 sticky | 文件属主 | 写入者 | 结果 |
|---|---|---|---|
| 有 | `lckfb` | root | ❌ |
| 有 | `root` | root | ✅ |
| 无（`~/perm-lab`） | `lihaihui` | root | ✅ |

**设计意图**：防「共享目录投毒」——攻击者在 `/tmp` 预置同名文件，诱使 root 程序以 root 权限写入。
`cat` 后内容变成攻击者写的东西（`>` 会 O_TRUNC 清空重写），这就是危害。

**教训：权限模型不止一层**

```
第 1 层  DAC 九位（属主/属组/other）        ← 本节主体
第 2 层  sticky bit（目录级：管删除 + 管 O_CREAT）
第 3 层  capabilities（CAP_DAC_OVERRIDE 让 root 绕过 DAC）
第 4 层  LSM / protected_* 加固（不给 root 开后门）
```

> 上层检查会在下层放行之后继续拦截。
> 遇到「权限都对却仍 Permission denied」，先查：`ls -ld <目录>`（有没有 `t`）+ `cat /proc/sys/fs/protected_regular`

### 坑 2：实验场地选错

`/tmp` 有 sticky + 额外规则，**不是干净的权限实验场地**。
以后做文件权限实验，用私有目录：`mkdir -p ~/perm-lab`。

### 坑 3：用 0 字节文件验证"能否读"

`cat` 成功也是空输出，肉眼分不清"读到了空文件"和"什么都没发生"。
**要看退出码**：`cat f; echo "exit=$?"` → `0`=成功，`1`=失败。

> 这是嵌入式调试的基本功：**别靠"看起来对"，要靠可观测的量**（退出码/计数器/时间戳）。
